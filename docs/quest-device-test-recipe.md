# Quest on-device test recipe

The verified procedure for putting a scene on a Quest 3 and looking at it.

**Why this file exists.** This flow was run a dozen times in one session and got
broken a dozen different ways — never the same way twice, and never by anything
the compiler or the test suite could catch. Each trap was rediscovered from
scratch because none of them were written down. Every "Trap" below cost real time
at least once.

---

## The procedure

```bash
# 1. Build + package, bundling a scene directory (must contain scene.json;
#    an assets/ subdir is optional).
#    PowerShell, from the repo root:
./android/quest/build.ps1 -SceneDir C:\path\to\scene_dir

# 2. Install.
adb install -r android/quest/build/xrds-app.apk

# 3. Clearing app data is no longer needed for scene iteration (ASSET_STAMP handles
#    it, see Trap 1). Still useful to exercise a genuinely cold first run.
# adb shell pm clear org.openxrds.devicesdk

# 4. Start capturing BEFORE launching — see Trap 2.
adb logcat -c
adb logcat -v time > /path/to/run.txt &

# 5. PUT THE HEADSET ON, then launch — see Trap 3. Full class name required.
adb shell am start -n org.openxrds.devicesdk/android.app.NativeActivity
```

Recover a frozen headset with `adb shell am force-stop org.openxrds.devicesdk`.

## Verifying the run from the log

```bash
grep -o "asset extraction complete.*"        run.txt   # N written / N failed
grep -o "assets already extracted.*"         run.txt   # stamp matched, loop skipped
grep -o "loaded '[^']*' — [0-9]* entities"   run.txt   # node count matches?
grep -c "panicked at"                        run.txt
grep -o "root_pos=[A-Za-z]*"                 run.txt | sort -u   # None => no AppCamera
grep -o "AdapterInfo {.*}"                   run.txt | head -1   # backend/GPU
```

## Traps

### 1. The asset cache compared file size only — **FIXED**

Kept because the symptom is worth recognising if it ever returns.

`android_main`'s extractor used to skip a cached file when
`cached_size == Some(bytes.len())`. Editing an asset without changing its byte length
left the device on the old one, and reinstalling did **not** help — the cache lives in
app data, not the APK. Android does not clear app data on APK upgrade either, so this
was a shipping bug, not merely a dev-loop annoyance.

Now keyed on `ASSET_STAMP`, a per-build marker generated by `build.sh`/`build.ps1`. It
changes every build, so it cannot false-match; a mismatch re-extracts everything
unconditionally. `pm clear` is **no longer needed** when iterating on a scene.

It is also faster than what it replaced: the old check read and decompressed every
asset out of the APK before deciding to skip the *write*, so it paid the expensive
half regardless. A stamp match now skips the loop entirely.

Verified on device: a byte-length-identical `scene.json` edit (4419B → 4419B, one
extra node) with no `pm clear` went from `4 entities` to `5 entities`. Under the old
code it would have stayed at 4.

### 2. logcat must be streaming before launch

Per-frame `XR-DIAG`/`naga` debug output rotates the ring buffer within seconds, so
`adb logcat -d` after the fact loses startup entirely. Stream to a file first.

Also: `log::` output lands under tag **`xrds`**, while `println!`/`eprintln!` land
under **`RustStdoutStderr`**, and some `tracing` events arrive with a target like
`event <src-path>`. Filtering on one tag hides the others — prefer no `-s` filter
and grep the file.

### 3. Wear the headset before launching

Launching while the headset is off, then donning it, aborts Bevy:
`uniform_buffer.rs:312` (`write_buffer_with(..).unwrap()`), then a queue-submission
timeout, then a panic in a destructor. Reproduces with no particle crate present — a
pre-existing Android lifecycle bug, tracked in
`docs/deferred/android-window-lifecycle-plan.md`.

Do **not** chase this via `adb`-driven pause/resume: `KEYCODE_HOME` + relaunch
destroys and recreates the native window cleanly, with zero panics and a correct wgpu
surface reconfigure. Only physically donning the headset triggers it, so the cause is
narrower than "the surface was recreated". Note also that `lifecycle=Suspended` is the
normal steady state for a Quest app and is not a symptom.

An unworn headset is also throttled to roughly one frame per 10s
(`DOFF_FROM_GUARDIAN` in the system log, `bevy_time::virt ... skipping ~9.8s`).
Do not diagnose a "stall" without checking whether it was simply off your head.

### 4. The spawn is `(0, 1.6, 8)`, not the origin

`SpawnConfig::default`. Authoring content at `z ≈ -1.5` — the intuitive "1.5m in
front" — puts it **9.5m away**, where a 1.2m separation subtends ~7° and reads as
one distant blob. Place content near the spawn, not near the origin.

### 5. Facing cannot be authored in XR

Initial yaw comes from LOCAL_FLOOR recentring, i.e. from however the headset
happened to be oriented at launch. "In front of the player" is not something a
scene can express. Either expect to look around, or place content so it is
findable from any facing (overhead works; a ring works).

### 6. An `InteractionZone` draws nothing

An unmarked trigger volume is indistinguishable from a broken trigger — "nothing
happened" reads identically. Put a visible pad or marker mesh at the same place.

### 7. `cargo check --workspace` does not cover the Android target

`android_main` and everything it calls is `#[cfg(target_os = "android")]`. A
desktop check passes while the Quest build is broken. Cross-compile before
believing the tree is healthy:

**Run the build script, not the bare cargo command.** `build.ps1`/`build.sh` export
`CMAKE_GENERATOR=Ninja` + `CMAKE_MAKE_PROGRAM` (`build.ps1:130`) before invoking cargo,
because `quiche`'s vendored BoringSSL builds through CMake, and on a Windows host CMake
otherwise picks a Visual Studio generator that cannot drive the NDK clang:

```
-- Check for working C compiler: .../ndk/.../clang.exe - broken
```

An earlier revision of this file recommended the raw command below, which fails for
exactly that reason — the documented health check did not work:

```bash
# DOES NOT WORK on its own — no CMake generator set
cargo ndk -t arm64-v8a -P 32 -o android/quest/jni build --release \
    -p xrds-app --no-default-features
```

Use `./android/quest/build.ps1` instead (add `-SceneDir` when bundling a scene).

**A failed CMake configure poisons the cache.** Once the broken-compiler probe has run,
`CMakeCache.txt` persists in the target dir and every later attempt fails identically
even after the environment is fixed. Delete the stale build dirs:

```bash
rm -rf target/aarch64-linux-android/release/build/quiche-* target/release/build/quiche-*
```

Two regressions hid here in one session: a duplicated `android_main`, and a
deleted `PostStartup` registration.

### 8. Deleting a system registration is silent

`app.add_systems(PostStartup, (spawn_app_camera, spawn_controller_visuals))`
was accidentally removed. The functions still compiled; nothing referenced them.
Result: no `AppCamera`, therefore no `OpenXrPlayerRoot`, therefore no controller
locomotion, no controller visuals, no initial anchor — while effects still
rendered, because the XR eye cameras come from `xrds-openxr` independently.

The dead-code warning was useless: the host `[lib]` target already reports these
functions as unused, since `main` itself is unused there.

**Tell:** `[XR-DIAG] update_view_proj#N: cam_count=2, root_pos=None`. A `None`
root means no player-root entity exists. `root_pos` staying constant while the
stick is pushed means input is not reaching locomotion.

### 9. Editing scripts with index-based text splicing

Three of the breakages above came from patching source by finding a start and end
marker and splicing. When the end marker occurs *before* the start marker,
`s[:start] + new + s[end:]` silently **duplicates** a region instead of replacing
it. Prefer anchored replacement of an exact block, and re-read the file afterwards.

### 10. Not every trigger kind can be fired by the player

**Fixed 2026-08-18** — the player now gets a kinematic capsule and the reserved id 0,
so `ZoneEnter` works; verified by walking onto a marked pad on a Quest 3. See
`docs/done/player-body-collider-plan.md`.

Historically: `ZoneEnter`/`ZoneExit` go through avian3d collision events, and the player
had no collider, so walking into an `InteractionZone` fired nothing at all — which reads
exactly like a mis-placed volume.

**Zone events are logged as of 2026-08-19.** They previously printed nothing, so a
zone could only be judged visually and "nothing happened" was unreadable. Both
outcomes now appear at `info!`, which matters because the deployed runtime runs at
`Level::INFO` (`runtime.rs:178`) — a `debug!` line would be invisible on device,
which is the one place this needs reading:

```bash
grep -oE "\[zone\] (ENTER|EXIT) .*"  run.txt   # the event fired, with both ids
grep -oE "\[zone\] .* dropped: .*"   run.txt   # collision occurred, id unresolved
```

The second is the important one. A drop means the collision **did** happen and an
id was missing — an id-registration gap, not a mis-placed volume. Only the first
drop logs at `info!` (further ones fall to `debug!`), because unregistered entities
overlapping a zone is legitimate and warning on each would be noise.

So the three states are now distinguishable from the log alone, without a rebuild:
no `[zone]` line at all = no collision; `dropped` = collision but no id; `ENTER` =
the event reached the runtime, so look at the Track binding next.

```bash
grep -oiE "grabbed|\[zone\] ENTER|fire_and_stop" run.txt | sort | uniq -c
grep -c "trigger-action.*did nothing"           run.txt   # 0 = the action found its target
```

## Generating a test scene

Hand-written `scene.json` drifts from the schema. Generate it with the real API
instead, via an env-var-gated test (inert during a normal `cargo test`):

```bash
XRDS_GEN_DEVICE_SCENE=/path/to/scene_dir/scene.json \
    cargo test -p xrds-scene-graph xxx_gen -- --nocapture
```

See `crates/xrds-scene-graph/src/tests/gen_device_check_scene.rs`. Keep the file;
treat its contents as scratch and rewrite the body for whatever you are checking.
